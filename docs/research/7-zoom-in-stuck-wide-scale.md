# 範囲の広い点群でホイールズームイン・右ドラッグ移動が一定倍率後に効かなくなる

- 関連Issue: #7
- 調査日: 2026-09-29

## 目的・背景

Issue #5 で「ホイールズームインを繰り返すと効かなくなる」「右ドラッグのパンも効かなくなる」現象を
一度修正した（[docs/research/5-zoom-in-stuck.md](5-zoom-in-stuck.md)）。修正内容は次の2点。

1. `controls.minDistance` を `minDistanceForSize(size) = Math.max(1e-6, size * 1e-6)` に設定し、
   `OrbitControls` 自身のカーソル位置中心ズームが浮動小数点の丸め誤差で完全に止まる前に、
   十分小さいが正の値でクランプする。
2. クリック位置中心回転（Issue #3）終了時の `target` 置き直し距離を `minDistance` 未満に
   ならないようクランプする（`computeTargetAfterRotate()`）。

Issue #5 の検証はシーン対角長 `size` ≈ 51.5 程度の点群（教室スキャン）で行い、実機で解消を確認した。
今回、**範囲の広い（スケールの大きい）点群**を読み込んだ場合に、同種の「ズームイン・パンが効かなくなる」
症状が再発したと報告があった。`minDistanceForSize()` は `size` に比例する値のため、`size` が
大きい（広範囲の）点群では下限値も比例して大きくなる。ユーザーが望む詳細レベルまでズームインする
before に下限へ到達している可能性が高いが、以下の理由から**確証はない**ため、本調査で切り分ける。

- `camera.near`（`size / 5000`）と `minDistance`（`size * 1e-6`）は `size` に対する比率が異なる
  （`near` は `minDistance` のおよそ5000倍）。`size` がどれだけ大きくなっても、両者の比は
  一定なので、`minDistance` に到達する**前に** `camera.near` によるクリッピングで点群が
  見えなくなる可能性の方が高い。この場合、体感としては「ズームインしても点群が消えるだけで
  距離自体は変化している」はずであり、Issue #5 で確認した「距離とminDistanceが完全一致して
  ズームが数学的に停止する」パターンとは異なる可能性がある。
- 一方で、広範囲点群では通常のホイール操作（数十〜数百ノッチ）で `size` から
  `minDistance`（`size * 1e-6`）まで到達するのに必要なノッチ数は `size` に依存しない
  （幾何級数的な縮小のため、比率が同じであれば必要回数も同じ）。したがって
  「一定倍率後に詰まる」という報告自体は、Issue #5 で対応した仕組みが `size` に関わらず
  同じように働いている可能性も残る。

## 調査内容（予定）

Issue #5 で追加したデバッグ情報パネル（`Viewer.getDebugInfo()` / ツールバー「デバッグ情報」ボタン）に、
本Issueの調査のため以下の項目を追加した。

- `near` / `far`（`camera.near` / `camera.far`）
- `sceneSize`（読み込み済み点群全体のバウンディングボックス対角長）

ユーザーの実機で範囲の広い点群を読み込み、ズームイン・右ドラッグパンが効かなくなった時点の
`distance` / `minDistance` / `near` / `far` / `sceneSize` を採取してもらい、以下を判定する。

- `distance ≈ minDistance` であれば、Issue #5 と同じ「`minDistance` クランプ自体が実用上の
  上限になっている」パターン。→ `minDistanceForSize()` の比率（`size * 1e-6`）を、広範囲点群でも
  ユーザーが望む詳細レベルに到達できるよう見直す（例: 比率を`size`非依存の絶対値にする、
  複数の下限候補のうち最大のものを採用する、等）。
- `distance ≈ near` かつ `distance > minDistance` であれば、`camera.near` によるクリッピングが
  先に発生している別パターン。→ `camera.near` の設定方針（`size / 5000`）自体を見直すか、
  ズーム時に動的に `near` を追従させる方式を検討する。
- どちらでもない場合は、別の要因（例: `far`超過によるクリップ、`sceneSize`の計算自体の問題等）を
  さらに調査する。

## 調査結果

実際の広範囲点群（道路沿いのRTK点群、`sceneSize` ≈ 7928.3）で再現し、デバッグ情報パネルで
以下の値を採取した。

| 状態 | distance | minDistance | near | far | sceneSize |
| --- | --- | --- | --- | --- | --- |
| 全体表示 | 7.9524e+3 | 7.9283e-3 | 1.585e0 | 3.9642e5 | 7.9283e+3 |
| ズーム途中 | 2.609e+3 | 7.9283e-3 | 1.585e0 | 3.9642e5 | 7.9283e+3 |
| **ズームイン・右ドラッグが効かなくなった瞬間** | **7.928e-3** | **7.9283e-3** | 1.585e0 | 3.9642e5 | 7.9283e+3 |

症状発生時、`distance` と `minDistance` はほぼ完全に一致しており（`7.928e-3` ≈ `7.9283e-3`）、
Issue #5 で確認した「`minDistance` クランプで数学的にズームが停止するパターン」が**同じ仕組みのまま
大きいスケールで再発している**ことが確定した。

同時に、`near`（1.585）は `minDistance`（7.9283e-3）のおよそ **200倍** であることも分かった。
この比率は `near = size / 5000`、`minDistance = size * 1e-6` という各々独立な計算式から導かれる
**定数**であり、`size` に依存せず常に近似的に200倍になる
（`(size/5000) / (size*1e-6) = 1 / (5000 * 1e-6) = 200`）。

つまり、カメラが `minDistance` に到達する**はるか手前**（`distance` が `near` を下回った時点、
このケースでは約1.585の距離）から、`camera.near` によるニアクリップで点群がレンダリングされなく
なる。教室スキャン（`size` ≈ 51.5）ではこのクリップ帯の絶対サイズが `near` ≈ 0.0103 と非常に
小さく体感されなかったが、今回のような広範囲点群（`size` ≈ 7928）では `near` ≈ 1.585
という無視できない絶対距離になり、「ズームインしていくと急に点群がすり抜けて消え、その先の
何もない空間に飛び込んでしまったように見える」（ユーザー報告の「過敏になって突き抜けてしまう」
という体感）として認識される。右ドラッグパンも `targetDistance`（≈カメラ・target間距離）に
比例して移動量が決まるため、`near` を下回った付近の極小距離帯でパン量が急激に小さくなり、
「動かしても反応が乏しい／逆に少し動いただけで大きく飛ぶように感じる」体感のブレにつながっている
と考えられる。

以上より、本Issueの根本原因は次の**2つの仕組みが両方とも作用**していることと判定する。

1. （Issue #5 と同一の仕組み）`minDistance` が `size` に比例するため、ズームを繰り返すと
   最終的に到達し、その時点でズーム・パンが完全に停止する。
2. （本Issueで新たに判明）`camera.near` と `minDistance` の比率が固定（約200倍）であるため、
   `minDistance` に到達する前に必ず `near` クリップ帯を通過する。このクリップ帯の絶対サイズは
   `size` に比例して大きくなるため、広範囲点群では「ズームインの終盤で点群がすり抜けて消える」
   ことが強く体感される。

## 結論・採用方針

`minDistance` を単純にさらに小さくするだけでは (1) は緩和されても (2) は解消しない
（`near` との比率が固定である限り、クリップ帯は必ず `minDistance` の手前に存在し続けるため）。
また `minDistance` を `near` に一致させる方針は Issue #5 で試して「詳細を見るためにズームインしたい
のにできない」という不満を招いた前例があるため採用しない。

そこで、**`camera.near` をズーム中の現在距離に応じて動的に再計算する**方式を採用する。

- `fitCamera()` 実行時に初期 `near`/`far` を設定するのは従来どおり（深度バッファ精度のため
  `far / near` 比を一定に保つ設計は維持）。
- `OrbitControls` の `change` イベント（もしくは毎フレームの `render()` 内）で、現在の
  `camera.position.distanceTo(controls.target)` を参照し、
  `near = clamp(distance / 100, MIN_NEAR, size / 5000)` のように**距離が縮むほど `near` も
  追従して縮む**よう再計算し、`camera.updateProjectionMatrix()` を呼び直す。
  `MIN_NEAR` は `minDistanceForSize(size)` 付近（`near` が `minDistance` を下回らない程度）の
  ごく小さい値とする。
- これにより、ズームインの過程で `near` が常に現在距離より十分小さい値を保つため、
  `minDistance` に到達するまでニアクリップで点群が消えることがなくなる。
  `minDistance` 自体は Issue #5 の値（`Math.max(1e-6, size * 1e-6)`）を維持し、ズーム・パンの
  最終的な安全下限としての役割はそのまま残す。
- `far` は現状の `size * 50`（固定）のままとし、ズームアウト側の挙動（Issue #5 以前から問題
  報告なし）には手を入れない。

反映先: [docs/detailed-design.md](../detailed-design.md) §3.7.3（後続の設計作業で追記）。
実装は本方針についてユーザーレビュー・承認後、TDD（`near` 再計算関数の単体テストを先に書く）で
着手する。

## 追加調査（近距離での動作確認時に判明: ホイールズームの「一気にズームイン」）

`near` 動的再計算を実装・実機確認する過程で、「ホイールをほんの少し触っただけで一気にズームインし、
点群を大きく突き抜けた位置まで飛んでしまう」という別の症状が報告された。`OrbitControls`
（`node_modules/three/examples/jsm/controls/OrbitControls.js`）のソースを確認し、以下の
仕組みを確認した。

- ホイール1回分のズーム倍率は `_getZoomScale(delta) = 0.95 ** (zoomSpeed * |delta * 0.01|)`
  （`zoomSpeed`既定値`1.0`）で決まり、`_dollyIn()`/`_dollyOut()`はこれを`this._scale`に
  **乗算**で累積する（`this._scale *= dollyScale`）。
- `update()`（毎フレーム、`render()`から呼ばれる）はその時点の`this._scale`を使って
  カメラ距離を1回だけ更新した後、**`enableDamping`の設定に関わらず無条件に`this._scale = 1`へ
  リセットする**。つまり回転・パン用の`dampingFactor`によるフレームをまたいだ滑らかな減衰は
  ズームには一切適用されない。
- そのため、**次の`update()`が呼ばれるまでに発生した全てのホイールイベントの倍率が
  乗算で積み上がり、1回の`update()`で一括して適用される**。通常はアニメーションループが
  約60fpsで回るため1フレーム内のホイールイベントは数個程度だが、大容量点群の読み込み・
  デコード処理（メインスレッドで動作）によってフレーム間隔が伸びている間にホイール操作を
  行うと、その間に蓄積した多数のホイールイベント分がまとめて一度に適用され、体感として
  「軽く触れただけで一気に大きくズームインする」ジャンプになる。今回の再現時、点群が
  69%→86%読み込み中（`progress`表示）だったことも、メインスレッドの混雑によりフレームが
  遅延していた状況と整合する。

### 対策方針

- **`controls.zoomSpeed`を既定値`1.0`から引き下げる**（例: `0.5`）。ホイールイベント1件あたりの
  倍率が`0.95`→`0.9747`相当に緩やかになり、同じ件数のイベントが積み上がった場合でも
  最終的な倍率変化が小さくなるため、フレーム遅延時の「一括ジャンプ」の体感も緩和される。
  `OrbitControls`公式APIの一部であり、副作用の少ない最小限の変更で導入できる。
- 長期的には、点群デコード・追加処理をより細かく分割してメインスレッドを長時間占有しない
  ようにする（アニメーションフレームを飽和させない）ことがより根本的な解決になるが、
  読み込みパイプライン全体の変更は本Issueのスコープを超えるため、今回は対象外とし、
  フォローアップとして [Issue #8](https://github.com/hinosrvy/pointcloud-viewer/issues/8) に
  切り出した。

## 追加調査2（`zoomSpeed`引き下げでも改善せず: クリック位置基準のズーム・移動への変更）

`zoomSpeed`引き下げを実機確認した結果、体感の改善が得られなかった。`zoomToCursor = true`は
ズームの**方向**（カーソル位置に向かって進む）のみをカーソルに追従させており、1回あたりの
ズーム**歩幅**（`radiusDelta`）は常に`OrbitControls`内部の`_spherical.radius`（＝カメラ・
`target`間の距離）に比例したままである。広範囲点群では`target`が最初にフィットした際の
シーン中心のまま固定されがちで、ユーザーが実際に見ている・操作したい領域から離れているほど
「歩幅は大きいがピンポイントで狙った位置には届かない」体感になり、`zoomSpeed`をいくら
下げても解決しない。

ユーザーからPotreeViewer等で採用されている、クリック位置を基準に`target`を都度再設定する
方式の提案があり、採用する。

### 採用する設計

- **シングルクリック（ドラッグ・計測モードに関わらず、ヒットした場合は常に）**:
  `pick()`でヒットした点を新しい`controls.target`とする。以後のズーム歩幅・パン量の基準が
  直近でクリックした場所に更新されるため、`target`が遠くに固定されたままになる問題を解消する。
- **ダブルクリック**: ヒットした点を`target`にする（上記と同じ）のに加えて、カメラをその点まで
  現在距離の**半分**まで近づける（`minDistance`未満にはしない）。PotreeViewer等と同様の
  「ダブルクリックでズームイン」操作を提供する。
- 実装は`computeDoubleClickZoomPosition(cameraPosition, hitPoint, minDistance)`という純粋関数に
  切り出し、ユニットテストで検証する。ポインタイベントの配線自体（`onPointerUp`/`dblclick`）は
  WebGL依存で単体テスト困難なため、[CONTRIBUTING.md](../CONTRIBUTING.md) §6の例外規定に基づき
  対象外とする。

## 追加調査3（実機確認: ズームを繰り返すとdistanceがminDistanceを大きく下回り操作不能になる）

追加調査2の実装後、実機で「ズームインを繰り返す→ある状態のまま以降ズームイン・移動・
ダブルクリックズームのいずれも効かなくなり、ズームアウトでしか脱出できない」現象が再発した。
デバッグ情報パネルで確認したところ、以下の値が観測された（スクリーンショットより）。

```
distance:    7.0293e-9
minDistance: 7.9283e-3
near / far:  7.9283e-3 / 3.9642e+5
controlsEnabled: true / rotateCandidate: false / rotateActive: false
```

**確認できた事実**: `distance`（カメラ・target間の距離）が`minDistance`を6桁以上下回っている。
`OrbitControls`は`update()`内で`_clampDistance()`により`spherical.radius`を`[minDistance, maxDistance]`
にクランプしているはずであり（`node_modules/three/examples/jsm/controls/OrbitControls.js`で
実装を確認済み）、本来この不変条件（`distance >= minDistance`）は毎フレーム維持されるはずである。

**仮説（未確定）**: `zoomToCursor = true`のとき、`OrbitControls`内部ではクランプ済みの半径を
`target`中心の球面座標としてではなく、カーソル方向へのレイ（`_dollyDirection`、ホイールイベント発生時の
マウス位置をアンプロジェクトして算出）に沿ってカメラ位置を直接移動させる経路がある
（`_handleMouseWheel` → `_updateZoomParameters` → `_dollyIn`/`_dollyOut` → `update()`内の
cursor-zoom分岐）。この移動方向は`target`方向の軸と厳密には一致しないため、`target`を
外部から任意の位置へ書き換える本機能（クリックで毎回`target`を再設定する）と組み合わさった際に、
クランプ済みの半径を前提とした計算がずれ、結果的な`camera-target`間距離が`minDistance`を
下回りうるのではないかと推測している。ただし、この内部メカニズムそのものを再現テストで
確定するには至っていない（three.js内部の詳細な条件分岐の組み合わせに依存するため）。

**採用する対策**: 原因の完全特定を待たず、観測された不変条件違反（`distance < minDistance`）を
`render()`側で毎フレーム強制的に是正する防御的なクランプを追加する。`controls.update()`の直後に
`camera.position`と`controls.target`の距離を再計算し、`minDistance`を下回っていれば
同じ方向を保ったまま`minDistance`まで押し戻す（`clampCameraDistance()`として純粋関数に切り出し、
ユニットテストで検証）。方向ベクトルが定まらないほど縮退している場合は、カメラの現在の視線方向
（`camera.getWorldDirection()`の逆）をfallbackとして使う。

この対策は、Issue #5で採用した`computeTargetAfterRotate()`（回転終了時にtarget側を防御的に
クランプする）と同じ設計思想を、より汎用的に「毎フレーム・カメラ側からの防御」として適用したもの。
内部の正確な発生条件が今後変化しても、不変条件そのものを保証することで同種の「操作不能」症状の
再発を防ぐ狙いがある。

## 追加調査4（ダブルクリックズームを滑らかにする）

ダブルクリックズームが瞬時にカメラを移動させる実装だったため、視点が把握しづらいという指摘を受けた。
`easeOutCubic`による減速イージングで、カメラ位置と`target`を約300msかけて補間するアニメーションに
変更した（`easeOutCubic()`として純粋関数に切り出し、ユニットテストで検証）。

## 追加調査5（シングルクリックのtarget更新を撤回し、ダブルクリックの見た目も修正）

追加調査4の実装後、実機で以下2点の不自然さが報告された。

1. シングルクリックした地点が画面中心へ移動してしまう。
2. ダブルクリックズームの動作も不自然に感じる。

**原因**: `controls.target`を書き換えると、`OrbitControls.update()`が毎フレーム無条件で呼ぶ
`camera.lookAt(target)`により、次のフレームで必ずその点が画面中心へスナップする。追加調査2で
「シングルクリックで毎回`target`を更新する」設計を採用した際、この副作用を見落としていた。
ダブルクリックズームの`onDoubleClick()`も同様に`target = hit`としていたため、アニメーション完了後に
同じスナップが発生し、さらにシングルクリックの`target`更新と組み合わさることで、意図と異なる
タイミングで視点が動いているように見えていた。

**対策**:
- **シングルクリックの`target`更新は撤回**した。`onPointerUp()`では`pick()`の結果を
  `onPick`コールバックに渡すのみとし、`controls.target`には触れない。
- **ダブルクリックズーム**は、`target`をクリック地点そのものではなく、
  「現在の視線方向（`camera.getWorldDirection()`、変更しない）上の、ズーム後のカメラ位置から
  クリック地点までの距離だけ進んだ点」に設定するよう変更した。視線の向きを一切変えずカメラを
  その方向に前進させるだけになるため、クリックした点は画面上の同じ位置に留まったままズームする
  （ホイールの`zoomToCursor`と同じ見え方）。アニメーション中に呼んでいた`camera.lookAt(target)`も
  削除し、視線方向をアニメーション開始時のまま完全に固定した。

この結果、`target`は「ダブルクリックでズームインしたときだけ、視線方向に沿って更新される」
という単純な仕様になった。広範囲点群でズーム歩幅が意図通りにならない問題（追加調査2の動機）は、
ダブルクリックズームによる`target`更新のみでも一定程度緩和される想定である。
